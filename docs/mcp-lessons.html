Field notes · Model Context Protocol · written from a build

MCP for product people

I built an MCP server that four Claude agents played a game-theory simulation through — 1,040 model decisions, about $19 of API spend, and a lot of things that broke quietly. This is what I would want to know before the next one, and what I would say if asked about it.

Everything here is from that build. Where a lesson cost money or a wrong result, it says so.

1

What MCP actually is, without the spec language

MCP is a standard for letting a model call your software. That's it. The value is that it's a standard: you describe your capabilities once, and any MCP-speaking model can discover and use them without you writing a bespoke integration per model.

The mental flip that matters for a PM: your product becomes the server, and the model becomes the user. You are no longer designing screens for a human who can tolerate ambiguity. You are designing an API for a reader that takes your wording literally, has no memory between calls except what you return, and pays by the token for everything you send it.

model (client) your system (server) │ │ │ "what can you do?" │ │ ─────────────────────────────────► │ tool list + descriptions │ ◄───────────────────────────────── │ + JSON schemas │ │ │ call harvest(amount=0.3) │ │ ─────────────────────────────────► │ you run the logic │ ◄───────────────────────────────── │ you return JSON │ │ the model decides WHICH tool and WHEN. You decide what exists, what it's called, what it says it does, and what comes back.

Four things are entirely yours, and each one is a product decision rather than an engineering one:

You controlWhy it's a product decision
Which tools existYou are defining the action space. An agent cannot do what you did not expose.
What they're calledNames carry meaning the model acts on. Ours cued an entire domain we were trying to hide.
The descriptionsThis is prompt engineering wearing a documentation costume. Length and enthusiasm change usage rates.
What you returnThe agent can only reason about what's in the response. Omitting a field silently removes a behaviour.

The shape of what we built

A shared-resource simulation. Four agents graze one field over 65 turns, can talk to each other, can form binding-ish agreements, and can fine each other. Each agent is an independent MCP client with its own bearer token.

15 tools, split by what they cost the agent: FREE READS look_around · get_status · listen_for_messages (no turn used) get_history · get_ledger · get_pacts ONE PER TURN harvest · move · plant · punish · pass_turn FREE CHANNELS say (one message per turn) propose_pact · accept_pact · leave_pact

That split is the whole design. Making observation free and action scarce is an economic choice expressed through an API: it means an agent is never punished for thinking, only for acting. Giving speech and agreements their own channels means an agent can negotiate and eat in the same turn — if talking had cost a turn, we would have been measuring the price of coordination rather than whether coordination happens.

3

Ten things the build taught me

1 · Tool descriptions are product copy, not documentation

Our pact tools had the longest, warmest description in the set — "offer a public agreement that members take no more than that per turn" — while every other action got one clipped line. All four agents proposed a pact on turn zero, before anything had happened. Flattening the wording to match the others was a deliberate debiasing step.

Transferable: if a tool is described more attractively than its neighbours, it gets used more. Audit descriptions for relative enthusiasm, not just accuracy.

2 · Tool names leak semantics you cannot write your way out of

We tried to test whether agents were reasoning or just recognising a famous scenario, so we rewrote every prompt and description into neutral language. The tools were still called harvest and plant. The framing survived.

Transferable: names are part of the prompt. Choose them for what they imply, not just what they do.

3 · Check the affordance before blaming the user — then check again

Agents never used the punishment tool. I called it a behavioural finding, then discovered get_pacts returned who was in an agreement but never who had broken one. The data required to act wasn't in the response; I'd written the intent in a comment and never implemented it.

So I fixed it — breaches now arrive itemised, agreed 0.3, took 0.55 — and re-ran. Forty-four breach notices were delivered and the agents still never punished anybody. Nor in the run where punishing a promise-breaker was fined at double rate, nor in the one where they were told to finish ahead of each other and lowering a rival directly raised their own position. Four conditions, 1,040 decisions, zero fines.

Transferable: two lessons, and the second is the one people miss. Never conclude "they don't use it" until the information needed to use it is in the response — and never assume fixing the affordance will change the behaviour. I had the right answer for the wrong reason, and only found out because I fixed the bug and re-measured instead of declaring victory.

4 · The default failure mode is a silent no-op, not an error

Four separate times, a change produced plausible-looking output with nothing happening: a config split the database so every action was rejected while the run "succeeded" at turn 0; a renamed field made a loop iterate zero times; a missing import turned one tool into an error string the agent read and ignored. Traditional monitoring saw green.

Transferable: agents swallow errors — a failed tool call comes back as text and the agent carries on plausibly. Assert on outcomes (did the world change?), never on absence of exceptions.

5 · Multi-agent coordination is yours to build

The protocol has no notion of "wait for the other three". Our game resolves all four agents' moves simultaneously, so we built a barrier: each call writes an intent, blocks, and releases when everyone has submitted or a timeout fires and absentees are recorded as passing.

Transferable: MCP gives you request/response. Turn order, fairness, deadlock and timeout policy are product decisions you own.

6 · Stateless by design, so identity rides on every call

The 2026 spec removed protocol-level sessions. Every call must be answerable from a bearer token plus your database. That sounds like a constraint and is actually a gift: a server restart mid-run loses nothing except the in-flight barrier.

Transferable: design for "any call could be the first call". It makes horizontal scaling and crash recovery nearly free.

7 · Every field you return has a price, per call, per agent, per turn

We were pretty-printing a JSON blob in each response. Removing the indentation cut input tokens by about a quarter. Separately, the server was re-expanding a compact grid into verbose records — 180 characters where 122 would do, on every single call.

Transferable: payload size is a recurring cost line, not a one-off. Multiply by agents × turns × runs before deciding a field is cheap.

8 · Cost per call is a moving target you must re-measure

I estimated $0.0029 per decision. After adding one feature it was $0.0048, and on a stronger model $0.0143 — a 5× swing. My "$1.40 for a run" estimate became $2.29 in reality. Every added field pushed it up.

Transferable: instrument token spend from run one and re-derive after every change. Do not extrapolate from an early sample.

9 · Model capabilities drift — ask, don't hardcode

Swapping models broke every call: the newer one takes an "effort" parameter, the older one takes an explicit token budget, and sending the wrong one is a hard 400. We replaced a hardcoded assumption with a capability lookup at startup.

Transferable: anything you hardcode about a model rots. Discover capabilities at runtime and fail loudly when they change.

10 · Exposed ≠ usable

Punishment existed from the start. In one run agents attempted it nine times and every attempt was refused, because the rule required standing next to the offender — and offenders are rarely adjacent. The feature was shipped, discoverable, and impossible to use.

Transferable: track attempted-and-rejected calls separately from successful ones. A high rejection rate on one tool is your clearest usability signal.

Interview questions and answers

Click any question. Answers are written the way I would actually say them — short, with a concrete example attached.

Fundamentals
What is MCP, in one minute?

It's a standard protocol for letting a model call your software. Your system runs a server that advertises a set of tools — each with a name, a description and a JSON schema — and the model acts as a client that decides which to call and when.

The point of a standard is that you integrate once rather than per model. The mental shift is that your product becomes an API and the model becomes the user — one that reads your wording literally and pays by the token for every byte you return.

How is it different from just giving a model an API to call?

Mechanically it's similar; the difference is discovery and uniformity. The model asks the server what it can do and gets back machine-readable schemas, so you don't hand-write per-model tool definitions or maintain them as models change.

What you don't get is anything above request/response. No sessions, no turn-taking, no coordination between clients. I built a barrier for multi-agent turn resolution myself — that's not something the protocol offers.

Walk me through the architecture you built.

An MCP server over streamable HTTP exposing 15 tools, with four Claude agents connecting as independent clients, each with its own bearer token. State lives in SQLite because the protocol is sessionless — identity has to be recoverable from the token on every single call.

The tools split three ways: free reads that cost nothing, one action per turn, and separate free channels for speech and for agreements. That split is the actual design — it decides what an agent is penalised for.

Why streamable HTTP rather than stdio?

stdio is one process per client, which is fine for a desktop integration. I needed four concurrent clients against one shared world, plus something deployable. HTTP gave me both, at the price of having to handle auth and concurrency myself.

Product judgement
How do you decide what to expose as a tool?

Same question as deciding what goes in a UI: what can a user do, and what must they know to decide? I'd add two rules specific to agents.

One — an agent can only do what you expose and only reason about what you return. We had a punishment feature nobody used, and the response never told agents who had broken a rule. I fixed that, delivered breaches itemised, and they still never used it — so the missing data was a real bug and not the reason. Both halves matter: check the affordance, then re-measure rather than assuming the fix worked.

Two — tool descriptions are prompt engineering. Our most warmly-described tool was used by every agent on the first turn. Description length changes usage rates, so I now audit them for relative enthusiasm, not just accuracy.

How do you know if an MCP feature is working?

Not by absence of errors, because agents swallow errors — a failed call comes back as text and the agent writes something plausible and continues. I'd track three things:

Attempt rate (is it being called at all), rejection rate (called and refused — our clearest usability signal; one tool was attempted nine times and refused nine times because the precondition was almost never satisfiable), and outcome assertions — did the world actually change. We had two full runs pass every superficial check while nothing happened at all.

How do you think about cost?

As a recurring line item, not a one-off. Every field you return is paid for on every call, by every agent, every turn. Removing pretty-printing from one JSON blob cut input tokens by a quarter.

And re-measure constantly. My per-decision cost went from $0.0029 to $0.0048 after one feature, then to $0.0143 on a stronger model. An early estimate I gave was wrong by 60% within a day.

How would you productionise this?

Three things I'd fix before anyone else touched it. Auth — bearer tokens per seat are fine for a closed demo, OAuth for real. Horizontal scale — my turn barrier is in process memory, so two replicas desynchronise silently; that state belongs in the database or a coordinator. And observability — I'd instrument tool attempt, rejection and latency per tool, since rejection rate was the most informative number I had.

Failure and debugging
Tell me about something that broke.

My favourite, because it looked like a result. Four agents played a full run, made every model call, exited cleanly — and finished at turn zero with nothing having happened. A config change had pointed two components at different database files, so every action came back "unknown token" and the agents just carried on.

It cost about $0.55 and taught me the real lesson of the project: in agent systems, broken things look like working things. A human files a bug. An agent writes a plausible sentence and continues. So I added a free dry run as a gate before any paid run, and made the loop abort after two consecutive rejected actions.

Tell me about a wrong conclusion you drew.

I reported that agents never enforce rules on each other and framed it as a finding about their behaviour. Then someone asked the obvious question — could they even see who had broken a rule? They couldn't. The response carried who was in an agreement and never who had violated one. I'd written the intent in a code comment and never implemented it, so it looked done.

The part I like is what happened next. I fixed it, re-ran, and they still never punished anyone — with breaches handed to them itemised, with promise-breaking fined at double rate, and in a condition where punishing a rival directly improved your own standing. So my original claim turned out to be true, and my reasoning for it had been wrong.

That's the habit I took away: a conclusion that survives fixing the bug underneath it is worth something. One that you never re-test is just a guess that happened to sound right.

How do you A/B test with agents?

Carefully, and with more replication than feels necessary. Two mistakes I made are worth stating.

The treatment leaked. I filtered a field out of one endpoint and forgot every action response carried the same field, so both arms were contaminated. Enumerate every channel a change has to cover and then assert the leak is closed.

One seed proved nothing. I had a beautiful result on the first seed that reversed exactly on the second. Non-determinism means a single run is an anecdote, and I now treat any single-seed result as a hypothesis.

What surprised you most?

How much of what looked like agent behaviour was actually my API design. Agents didn't punish — because the data wasn't in the response. They all proposed agreements immediately — partly because that tool had the most enthusiastic description. They ignored a competitive objective entirely — 260 decisions, not one mention of being ahead.

Every time I thought I'd found something about the model, at least half of it was something about the interface I'd built. The exception proved the rule: the refusal to punish survived every fix I threw at it — visibility, a doubled penalty, a reachability change, and an objective where punishing paid. That one really was the model.

The sharp ones
Why MCP rather than function calling directly?

For a single model and a handful of functions, direct function calling is simpler and I'd use it. MCP earns its keep when you have multiple clients, want the tool surface to be discoverable rather than hand-declared per integration, or expect to swap models.

I'd be honest that it isn't free: you take on auth, concurrency and transport that a direct integration wouldn't have made you think about.

What would you do differently?

Instrument before building. I added token tracking after the first paid run and cost estimates after that, so my early numbers were guesses and one of them was wrong by 60%.

And I'd freeze the design sooner. I improved the system roughly eight times during the study, and each change invalidated the earlier results — I ended with several runs measuring worlds that no longer existed. There's a version of that project that never gets measured because the instrument keeps improving.

How do you stop an agent doing something expensive or destructive?

In code, not in a prompt. I had a hard budget ceiling checked before every model call and updated from usage after it — crossing it raises and stops the run rather than warning. Same for turn caps, so a runaway loop can't drain credit.

The principle: anything you'd write in a prompt as "please don't", an agent will eventually do. Constraints belong in the layer the agent cannot talk its way past.
